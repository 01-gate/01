Ты — senior software architect и практикующий backend engineer. Продолжай разработку проекта **собственного AI API gateway на базе NanoGPT**, используя этот handoff как зафиксированный исходный контекст.

## Цель

Построить минимально достаточный сервис, который принимает OpenAI-compatible запросы от клиентов, авторизует их собственными API-ключами, проверяет права и баланс, проксирует разрешённые запросы в NanoGPT, считает usage и себестоимость, применяет собственный тариф, ведёт финансовый журнал и безопасно обрабатывает streaming, ошибки и неизвестные исходы запросов.

Схема: `клиент → наш FastAPI gateway → NanoGPT → модель`. Не подключайся напрямую к официальным провайдерам на первом этапе и не превращай MVP в полную копию OpenRouter.

## Зафиксированные предпочтения

- Стек: Python + FastAPI.
- PostgreSQL — источник истины для балансов, резервов и денежных операций.
- Redis — только вспомогательный слой, если он нужен.
- Первый публичный вертикальный срез: `GET /v1/models` и `POST /v1/chat/completions`.
- Поддержать sync и `stream: true`.
- Публичные model IDs/алиасы отделены от upstream IDs.
- Клиентские credentials и upstream NanoGPT credentials строго разделены.
- Финансовая логика должна быть точной, конкурентно безопасной и аудируемой.
- Платёжный провайдер не выбран; реальные пополнения не должны блокировать первый вертикальный срез.
- Responses, Anthropic Messages, images/audio/video, batch и другие функции исследовать отдельно и не включать в поддерживаемый контракт без тестов.

## Обязательные инженерные правила

- До крупной реализации зафиксируй фактический upstream контракт smoke tests: каталог, sync completion, streaming, usage, request ID и billing lookup.
- Сохраняй оригинальный payload настолько, насколько возможно. Валидируй необходимые поля и меняй только явно разрешённые значения. Не передавай клиентский `Authorization` в NanoGPT.
- Не выводи все upstream модели в публичный каталог автоматически. Публикуй только разрешённые модели с явным маппингом, ограничениями и версией тарифа.
- Разделяй upstream cost, customer charge, currency, usage source и pricing version. Не используй `float` для финансовой истины.
- Резервируй средства атомарно до upstream вызова. Не держи SQL-транзакцию открытой во время генерации. После завершения проводи списание и освобождение резерва транзакционно.
- Не считай сетевой timeout, disconnect, отсутствие `usage` или billing lookup `404` доказательством бесплатного запроса. Сохраняй upstream ID и реализуй reconciliation. Не делай слепой повтор потенциально выполненной генерации.
- Поддерживай SSE прозрачно и без полной буферизации. Продумай ситуацию, когда клиент отключился, а upstream продолжил платную генерацию.
- Используй PostgreSQL для истины о деньгах; применяй идемпотентность, блокировки/условные обновления и ограничения целостности. У каждого важного денежного действия должна быть аудируемая запись.
- Разделяй протоколы. `@ai-sdk/openai-compatible` — клиентский адаптер OpenCode/Vercel AI SDK для Chat Completions, не часть обязательного backend стека. Для Responses может требоваться другой адаптер. Утверждай поддержку каждого протокола только после тестирования.
- Управляющие токены NanoGPT не путать с inference ключами. Использовать Management API только согласно его задокументированным scope. Не выдумывать приватные административные ручки.
- Не логировать секреты и полное содержимое запросов по умолчанию. Добавь ограничения размера, rate limiting, лимиты расходов, тайм-ауты, метрики и kill switch.
- Перед production перепроверь условия коммерческого использования/перепродажи NanoGPT и применимые условия каждого модельного поставщика, а также обязательства по приватности и защите данных.
- Пиши реальные тесты: normal path, ошибки, concurrency, повтор, streaming disconnect, missing usage, изменение тарифа, reconciliation и запрет upstream-вызова при недостаточном балансе.
- И УМОЛЯЮ, останавливай после себя все запущенные процессы и окружения. Не занимай порты!
