# Технический handoff: собственный AI API gateway на базе NanoGPT

**Версия:** 1.0  
**Дата фиксации контекста:** 21 октября 2026 г.  
**Назначение:** передача контекста следующему AI-агенту для исследования контрактов API, архитектуры и последующей реализации MVP.

---

## 1. Краткое техническое саммари

Разрабатывается собственный API gateway для платного доступа к языковым моделям. На первом этапе gateway не подключается напрямую к официальным поставщикам моделей: единственный планируемый upstream — NanoGPT.

**Целевая схема:**

`Клиент / SDK / Pi → наш API gateway → NanoGPT API → выбранная модель`

Наш сервис отвечает за клиентские API-ключи, авторизацию, публичный каталог моделей, ограничения, учёт запросов, собственный биллинг, обработку ошибок, диагностику и расчёт цены для клиента. NanoGPT выполняет запрос к модели и возвращает ответ и доступные сведения об использовании/стоимости.

**Предпочтительный стек:** Python + FastAPI, MongoDB как источник истины для денег и финансовых операций; Redis допустим для rate limiting, кеширования и вспомогательных задач, но не как единственное хранилище баланса.

**MVP не должен быть полной копией OpenRouter.** Начать с `GET /v1/models` и `POST /v1/chat/completions`, поддержать streaming, клиентские ключи, лимиты и корректный жизненный цикл биллинга. Остальные протоколы и возможности добавлять только после исследования их контрактов.

## 2. Правила работы агента

1. Работай как senior software architect и практикующий backend engineer. Переходи от анализа к конкретным проверяемым изменениям.
2. Не задавай уточняющих вопросов, если можно принять безопасное допущение. Записывай допущение и отдельно перечисляй вопросы, действительно блокирующие работу.
3. Для актуальных возможностей NanoGPT, Pi и сторонних моделей используй официальную документацию и, где это безопасно, реальные HTTP-проверки. Приводи источники для внешних утверждений.
4. Различай **подтверждённый факт**, **наблюдение из предоставленного примера**, **проектное решение/допущение** и **открытый вопрос**.
5. Не выдумывай endpoint'ы, поля, ID моделей, схемы ошибок, разрешения токенов, тарифы и гарантии биллинга.
6. Не смешивай Chat Completions, Responses и Anthropic Messages: совместимость с одним протоколом не означает совместимость со всеми остальными.
7. Не передавай клиентский `Authorization` поставщику. Upstream-аутентификация должна формироваться на сервере.
8. Никогда не раскрывай upstream-ключи и не записывай их в логи. Не позволяй обходить авторизацию, лимиты, резервы и списания.
9. Не переусложняй MVP. Предпочитай минимальные компоненты с чёткими интерфейсами расширения.
10. При реализации давай цельный код, миграции, тесты и инструкции запуска. Не подменяй реализацию одной архитектурной дискуссией.
11. При расхождении документации и фактического поведения зафиксируй расхождение и создай воспроизводимый контрактный тест.

## 3. Известные факты и границы уверенности

### 3.1. NanoGPT API: подтверждено документацией на дату фиксации контекста

Официальные точки входа:

- API overview: https://nano-gpt.com/api
- Полная документация: https://docs.nano-gpt.com/introduction
- Chat Completions: https://docs.nano-gpt.com/api-reference/endpoint/chat-completion
- Pi config schema: https://pi.dev/schemas/models.schema.json

Документация NanoGPT описывает, в частности, следующие endpoint'ы:

| Метод и путь | Назначение | Статус в рамках MVP |
|---|---|---|
| `POST /api/v1/chat/completions` | OpenAI-compatible Chat Completions; документация указывает streaming, tools и vision | Основной endpoint |
| `GET /api/v1/models` | Каталог моделей; `?detailed=true` заявлен для цены и лимитов контекста | Нужен для исследования и синхронизации каталога |
| `POST /api/v1/responses` | OpenAI Responses API | Исследовать; не считать частью MVP автоматически |
| `POST /api/v1/messages` | Anthropic Messages API | Исследовать для будущей совместимости |
| `GET /api/v1/usage` | Агрегированный usage для API-ключа, которым подписан запрос | Полезен для сверки; не возвращает сырые записи всех запросов |
| `GET /api/v1/usage/requests/{request_id}` | Поиск сведений о первичном списании и токенах по request ID; документация указывает окно 24 часа | Важен для сверки неоднозначных запросов |
| `/api/management/v1/...` | Отдельный Management API с отдельными scoped management tokens | Исследовать отдельно, не использовать как inference API |
| `POST /api/v1/embeddings` | Embeddings | За пределами первого MVP |
| `POST /api/v1/images/generations` | OpenAI-compatible image generation | За пределами первого MVP |
| `POST /api/v1/audio/speech` | Text-to-speech | За пределами первого MVP |
| `POST /api/v1/audio/transcriptions` | Speech-to-text | За пределами первого MVP |
| `POST /api/generate-video` | Асинхронная генерация видео; документация описывает отдельный жизненный цикл задания | Не включать в общий синхронный proxy без отдельного дизайна |

Официальная документация принимает inference API-ключ через `Authorization: Bearer ...` или `x-api-key`. Для server-to-server интеграции документация также рекомендует рассмотреть host `https://api.nano-gpt.com`, поскольку он рассчитан на более крупные запросы и длительные вызовы. В интерфейсе NanoGPT при этом указан base URL `https://nano-gpt.com/api/v1`. **Это различие необходимо проверить практическими smoke-тестами; не зашивать host в код без конфигурации.**

NanoGPT Management API отделён от inference API. Документация описывает `usage:read`, `api_keys:read` и `api_keys:write`; management token с `usage:read` не предназначен для запуска моделей и расходования inference-баланса. Обычный inference API-key не вызывает Management API.

Usage API возвращает агрегированные значения по авторизованному API-ключу и не является полным журналом каждой транзакции. Request Billing API предназначен для точечной проверки недавнего запроса по его ID. Согласно документации, временный `404` при сверке может означать, что учёт ещё не готов; `404` не доказывает нулевую стоимость. При stream failure документация рекомендует сохранять `X-Request-ID` и проверять биллинг вместо слепого повтора генерации.

### 3.2. Наблюдение из пользовательского примера ответа NanoGPT, не контракт для всех моделей

В предоставленном примере ответа встречались:

- `usage.prompt_tokens`, `completion_tokens`, `total_tokens`, `reasoning_tokens`;
- `completion_tokens_details`, `prompt_tokens_details`, `cached_tokens`;
- `usage.cost`, `currency`;
- `x_nanogpt_pricing.amount`, `currency`, `costUsd`, `usdCost`, `inputTokens`, `outputTokens`, `cacheReadInputTokens`, `cacheCost`, `requestId`, `usageSource` и прочие поля.

Это **только наблюдение по одному ответу**. Нельзя предполагать, что каждое поле присутствует во всех моделях, endpoint'ах и режимах streaming. Семантику полей и соответствие фактическому списанию необходимо подтвердить документацией и тестами.

Не складывать повторно пересекающиеся счётчики. В частности, reasoning tokens могут быть подмножеством output/completion tokens, а дополнительные поля детализации не обязательно взаимно исключаются.

## 4. Проектные решения для MVP

### 4.1. Публичный API нашего сервиса

Целевой интерфейс MVP:

- `GET /v1/models` — возвращать только модели, опубликованные и разрешённые нашим сервисом.
- `POST /v1/chat/completions` — принимать OpenAI-compatible Chat Completions, поддерживать `stream: false` и `stream: true`.

Это **наши запланированные публичные маршруты**, не заявление о новых endpoint'ах NanoGPT.

Клиент задаёт собственный ключ нашего сервиса и наш `baseURL`. На стороне gateway ключ валидируется локально. Затем сервис маппит публичный ID модели в точный upstream ID и отправляет запрос к настроенному upstream host с секретом NanoGPT.

Не отдавать клиенту upstream-специфичные внутренние данные (оптовую себестоимость, служебные метаданные аккаунта, чужие идентификаторы и секреты), если публичный контракт специально их не предусматривает. Ответ оставлять совместимым с объявленным протоколом.

### 4.2. Разделение обязанностей

- **API layer:** маршруты, валидация входа, совместимые ошибки и SSE.
- **Auth/access layer:** собственные API-ключи, пользователи, доступные модели, лимиты и rate limiting.
- **Model catalog:** публичный ID, upstream ID, возможности, ограничения, доступность и версия тарифа.
- **Upstream adapter:** HTTP-клиент NanoGPT, управление host/timeout, upstream Authorization, обработка ошибок и streaming.
- **Usage/billing:** нормализация usage, оценка резерва, фиксация фактической стоимости, цена клиенту и reconciliation.
- **Persistence:** MongoDB как источник истины для кошелька, финансового журнала и статуса биллинга.
- **Operations:** метрики, безопасные журналы, корреляционные ID, алерты и аварийное отключение.

### 4.3. Минимальная модель данных

Ожидаемые сущности (физическую схему спроектировать и обосновать при реализации):

- `users` — аккаунты;
- `api_keys` — хэши ключей, владельцы, scopes/права, статус, лимиты и дата отзыва;
- `wallets` — доступный и зарезервированный баланс;
- `ledger_entries` — неизменяемые проводки пополнений, резервов, списаний, освобождений, возвратов и корректировок;
- `api_requests` — публичный запрос, модель, status, usage, суммы, время и correlation ID;
- `request_attempts` — отдельные попытки upstream, upstream request ID, HTTP-статус и outcome;
- `models` — публичный ID, точный upstream ID, capabilities, лимиты и флаг доступности;
- `pricing_versions` — тарифы и правила, действующие для запроса;
- `payments` — будущая интеграция платежей; конкретного провайдера пока не выбирать.

Хранить `upstream_cost` и `customer_charge` отдельно. Сохранять currency, источник usage, версию тарифа, точный upstream model ID и upstream request ID там, где они доступны. Для финансовых расчётов использовать `Decimal`/SQL `NUMERIC` достаточной точности либо целые денежные единицы с достаточным масштабом; не использовать binary floating point как источник финансовой истины.

### 4.4. Жизненный цикл биллинга

1. Валидировать ключ, пользователя, модель, тело запроса, лимиты и максимальную допустимую стоимость.
2. Атомарно зарезервировать средства в БД. При неуспехе резервирования upstream-вызов не делать.
3. В короткой транзакции сохранить запись запроса/попытки, затем вне транзакции обращаться к NanoGPT. Не удерживать открытую SQL-транзакцию во время генерации.
4. Зафиксировать ответ, HTTP outcome, `X-Request-ID` и доступный usage. Вычислить сумму для клиента по версии тарифа, не путая её с upstream cost.
5. В отдельной короткой транзакции атомарно записать списание и освободить остаток резерва. Все шаги должны выдерживать конкуренцию и повторы.
6. Если результат/usage неизвестен, не помечать вызов бесплатным и не освобождать весь резерв автоматически. Перевести операцию в состояние вроде `pending_reconciliation`, сохранить upstream request ID и использовать документированный способ сверки. Названия статусов можно изменить при реализации, смысл должен сохраниться.
7. Идемпотентность нашего API защищает от повторной обработки клиентского запроса, но сама по себе не гарантирует идемпотентность генерации у upstream. После неоднозначного сетевого сбоя не делать слепой повтор.

### 4.5. Streaming и ошибки

Проксировать SSE по мере поступления без обязательного накопления полного ответа. Учесть нормальное окончание, отмену клиентом, обрыв сети, ошибку после первых chunks, отсутствие финального usage и disconnect после того, как upstream мог исполнить платный запрос.

Пропускать/нормализовать только те заголовки, которые нужны публичному протоколу. Не передавать upstream Authorization или внутренние заголовки. Сохранять внешний correlation ID и `X-Request-ID` upstream, если приходит.

Не повторять генерацию только на основании тайм-аута или обрыва. Коды и правила ретраев сверять с актуальным руководством NanoGPT; учитывать `Retry-After`, тип endpoint'а и возможность уже состоявшегося списания. Ошибка сверки или временное отсутствие billing record не равно доказательству нулевого расхода.

### 4.6. Авторизация, лимиты и безопасность

- Клиентские ключи нашего сервиса случайные; хранить только безопасное проверочное представление/хэш и показывать полный секрет только в момент создания.
- Отдельно хранить upstream API key в секрете окружения или менеджере секретов.
- Ограничивать body size, длительность, допустимые модели, output/context limits, concurrency, frequency и max cost/request.
- Вести структурированные безопасные логи без ключей, полного Authorization, секретов и по умолчанию без prompt/response.
- Защитить финансовые операции от race conditions, дублирования событий и повторной обработки.
- Иметь глобальный kill switch, лимиты дневных расходов и оповещения о необычной активности.
- Redis допустим как вспомогательный слой; MongoDB и финансовый журнал остаются источником истины.

### 4.7. Тарифы и пополнения

Тарифы клиента — самостоятельный коммерческий слой. Не считать `usage.cost` или поле расширения NanoGPT безусловно публичной ценой клиента. Предусмотреть тарифную версию, раздельные `upstream_cost` и `customer_charge`, точные денежные вычисления и воспроизводимый расчёт суммы.

Платежи не входят в обязательный scope первого вертикального среза, но схему следует не делать несовместимой с будущими пополнениями. При добавлении оплаты предусмотреть подтверждение на backend, идемпотентную обработку webhook, дубли событий, возвраты, reconciliation и аудит. Не выбирать провайдера без отдельного решения.

## 5. Неизвестные и обязательные проверки

1. **API host:** сравнить `https://nano-gpt.com/api/v1` из пользовательского примера/API-интерфейса и рекомендацию документации использовать `https://api.nano-gpt.com/api/v1` для API-key интеграций. Проверить `/models`, Chat Completions, размер тела и длительный запрос. Сделать host конфигурируемым.
2. **Модель:** `qwen/qwen3.7-flash`
3. **Usage в sync/stream:** проверить наличие и семантику `usage`, `cost`, `x_nanogpt_pricing`, cached/reasoning details и `X-Request-ID` для конкретных моделей и режимов. Не выводить общий контракт из одного ответа.
4. **Сверка:** проверить `GET /api/v1/usage`, `GET /api/v1/usage/requests/{request_id}`, окно доступности данных, поведение временного `404`, refunds и отличия primary charge от net cost.
5. **Management API:** определить необходимость этого интерфейса для нашего сервиса. Не предполагать, что он выдаёт account-wide transaction ledger или полный набор списаний; документация ограничивает Usage API агрегированным usage текущего ключа.
6. **Модельный каталог и цены:** установить, какие метаданные реально доступны через `/models?detailed=true`, как быстро меняются цены и как обнаруживать удалённые/недоступные модели.
7. **Протоколы:** отдельно проверить Pi с нашим `baseURL`, `GET /v1/models`, Chat Completions, SSE, инструменты и особенности reasoning. Не заявлять поддержку Responses/Anthropic Messages до реализации и тестов.
8. **Коммерческие условия и данные:** до production перепроверить действующие условия NanoGPT и условия отдельных модельных поставщиков на предмет перепродажи/реселлинга, допустимого использования, географии и передачи данных. Для выбранных рынков отдельно оценить GDPR/договоры обработки данных, сроки хранения, НДС и B2C/B2B обязанности с квалифицированным консультантом.
9. **Платёжный провайдер:** не выбран.
10. **Механика ценообразования:** размер наценки, возможная минимальная комиссия и округление пока не определены. Не вводить цифры от себя.

## 6. Стартовые curl-проверки

Использовать только собственный ключ из переменной окружения. Не включать `set -x` и не печатать значение переменной.

```bash
export NANOGPT_API_KEY="<your-key>"
# Выбрать host после проверки документации и smoke tests.
export NANOGPT_BASE_URL="https://api.nano-gpt.com/api/v1"

# Каталог моделей
curl --fail-with-body -sS \
  "$NANOGPT_BASE_URL/models" \
  -H "Authorization: Bearer $NANOGPT_API_KEY"

# Расширенные сведения о моделях, если endpoint отдаёт их для данного ключа/host
curl --fail-with-body -sS \
  "$NANOGPT_BASE_URL/models?detailed=true" \
  -H "Authorization: Bearer $NANOGPT_API_KEY"

# Небольшой синхронный тест: подставить model ID из фактического каталога
curl --fail-with-body -i \
  "$NANOGPT_BASE_URL/chat/completions" \
  -H "Authorization: Bearer $NANOGPT_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"<EXACT_MODEL_ID_FROM_CATALOG>","messages":[{"role":"user","content":"Reply with OK"}],"stream":false}'

# Агрегированный usage авторизованного inference API-ключа
curl --fail-with-body -sS \
  "$NANOGPT_BASE_URL/usage" \
  -H "Authorization: Bearer $NANOGPT_API_KEY"

# После запроса, если ответ/заголовки содержат X-Request-ID, сверить primary charge
export UPSTREAM_REQUEST_ID="<REQUEST_ID_FROM_RESPONSE_OR_HEADER>"
curl --fail-with-body -i \
  "$NANOGPT_BASE_URL/usage/requests/$UPSTREAM_REQUEST_ID" \
  -H "Authorization: Bearer $NANOGPT_API_KEY"
```

Для streaming повторить тестовый вызов с `"stream": true`, `Accept: text/event-stream` и `curl -N`; заранее убедиться, что точный model ID поддерживает нужные возможности. Платный вызов не повторять автоматически при тайм-ауте или разрыве соединения. Запрос `/usage/requests/{request_id}` документирован в ограниченном временном окне; его временный `404` не является доказательством нулевого списания.

## 7. Минимальный набор интеграционных проверок

- Запрос `GET /models` и `GET /models?detailed=true` с целевым host.
- Один non-stream Chat Completions запрос с точным model ID.
- Streaming запрос с фиксацией `X-Request-ID`, финального чанка и usage.
- Запрос с несуществующей/отключённой моделью и некорректным JSON.
- Недостаточный баланс нашего клиента: upstream не должен вызываться.
- Несколько одновременных запросов при балансе, достаточном только для части резервов.
- Повтор одного клиентского idempotency key.
- Отзыв клиентского ключа, запрет модели, rate limit и ограничение размера запроса.
- Обрыв до upstream-ответа, после первых stream chunks и после потенциального выполнения генерации.
- Отсутствующий usage и сверка по upstream request ID.
- Временный 404 при billing lookup: не считать подтверждением нулевого списания.
- Изменение тарифа между запросами: уже завершённый запрос сохраняет применённую pricing version.
- Ошибки upstream 401/402/403/404/408/409/413/429/500/503 с корректным отображением клиенту и безопасной политикой повторов.
- Проверка журналов и трасс: ни один секрет не должен попадать в лог.

## 8. Рекомендуемый порядок разработки

### Этап A. Исследование контракта

Сделать маленькие curl smoke tests для host, каталога, sync request, streaming, usage и billing lookup. Сохранить обезличенные реальные примеры успеха/ошибки и описать расхождения с документацией. Не переходить к широкому проксированию до фиксации минимального upstream-контракта.

### Этап B. Тонкий вертикальный срез без реальных платежей

Реализовать FastAPI-приложение, конфигурацию upstream, клиентские ключи, `GET /v1/models` и `POST /v1/chat/completions`. Использовать mock upstream в unit/contract tests; затем провести ограниченную интеграционную проверку NanoGPT. Для локальной разработки допустим тестовый пользователь с начальным внутренним балансом, но не включать публичные пополнения.

### Этап C. Биллинг и устойчивость

Добавить MongoDB-схему, журнал, атомарные резервы, окончательные списания, тарифные версии, состояния reconciliation, тесты гонок, неопределённых исходов и повторов.

### Этап D. Совместимость и эксплуатация

Проверить Pi через custom provider и правильный SDK-адаптер. Добавить безопасные логи, метрики и лимиты. Открывать доступ пользователям только после прохождения тестов биллинга и правил обработки незавершённых запросов.

### Этап E. Пополнения и расширение протоколов

После MVP выбрать платёжный провайдер, спроектировать идемпотентные пополнения и возвраты. Затем отдельно оценить Responses, Anthropic Messages и прочие endpoint'ы.

## 9. Критерии готовности MVP

- Клиент может использовать собственный API key и привычный OpenAI-compatible Chat Completions SDK.
- Сервис публикует только разрешённые модели с контролируемыми alias → upstream ID.
- Upstream secret не раскрывается и клиентский Authorization не проксируется.
- Баланс не может быть перерасходован конкурентными запросами из-за race condition.
- Все денежные операции прослеживаются в журнале, суммы воспроизводимы по версии тарифа.
- Streaming работает без полной буферизации, а disconnect/unknown outcome не ведёт к автоматическому бесплатному запросу или слепому дублю генерации.
- Для неизвестного upstream исхода есть понятный reconciliation flow.
- Пройдены unit, concurrency, error-path и upstream contract tests.
- Недостоверные и неподтверждённые свойства API явно отмечены как ограничения, а не рекламируются как поддержанные возможности.
