# Первый рабочий запуск NanoGPT Gateway через OpenCode

**Дата:** 2026-10-21  
**Статус:** реализация подготовлена; локальные тесты и live-проверка ожидают запуска в окружении проекта этапа

## Цель

Запустить gateway локально через Python virtualenv и использовать его как провайдера OpenCode для повседневной работы. Запросы должны идти по цепочке:

`OpenCode → FastAPI gateway → NanoGPT → модель`

На этом этапе gateway используется лично для практической проверки. Финансовый учёт и обслуживание сторонних пользователей не входят в задачу.

## Зафиксированный объём

1. Запуск на обычном Python + `.venv`, без Docker и без ручных `export`. Настройки gateway автоматически загружаются из проектного `.env`.
2. Реальные маршруты `GET /v1/models` и `POST /v1/chat/completions`, sync и SSE.
3. Собственный allowlist публичных моделей. На первом этапе сохраняется публичный ID `01`, сопоставленный с проверенным upstream ID `xiaomi/mimo-v2.6-flash`. Не раскрывать весь каталог NanoGPT.
4. OpenCode использует локальный провайдер gateway и публичную модель `01`.
5. Поддержать необходимые для работы OpenCode поля Chat Completions, включая function/tool calling: `tools`, `tool_choice`, `parallel_tool_calls`, а также tool-call данные внутри `messages`. Передавать только поля, контракт которых определён и проверяется; не добавлять другие протоколы.
6. SSE передаётся без полной буферизации; обычное завершение выдаёт единственный `[DONE]`. Ошибка после начала ответа не подменяет HTTP-статус и не маскируется под успешное завершение.
7. Не делать автоматических повторов генерации. При обрыве после отправки запроса сохранить доступные request IDs и зафиксировать неопределённый исход. Повторное подключение допустимо только если фактический контракт NanoGPT предоставляет способ продолжить тот же запрос без повторного запуска генерации; не предполагать наличие такого механизма.
8. Сохранить безопасные логи, закрытие ресурсов, таймауты и существующие проверки ошибок.
9. Документировать воспроизводимый запуск с нуля, настройку OpenCode, диагностику и smoke test.

## Контракт NanoGPT

- Использовать отдельный конфигурируемый inference base URL; текущая настройка по умолчанию проекта: `https://api.nano-gpt.com/v1`.
- Upstream Chat Completions вызывается по относительному пути `/chat/completions`.
- Upstream авторизуется серверным NanoGPT inference key. Клиентский ключ gateway используется только для локального маршрута `POST /v1/chat/completions`.
- Для streaming проверить SSE до `[DONE]` и usage, если он присутствует. Не считать отсутствие usage доказательством нулевой стоимости.
- Usage API и Request Billing, PostgreSQL, Redis, баланс, резервы, тарифы и финансовый журнал не реализовывать.

## Проверки

### Автоматические локальные тесты

- Все существующие тесты проходят.
- Tool-параметры и tool-call сообщения доходят до fake upstream без потерь.
- Sync и SSE сохраняют совместимый формат, включая tool-call chunks.
- Неизвестная модель и невалидный клиентский ключ не вызывают upstream.
- Ошибки upstream до начала SSE корректно отображаются как 502/504.
- Ошибка после начала SSE не вызывает повторной генерации и не добавляет фиктивный `[DONE]`.
- Отключение клиента закрывает upstream-ресурсы; повторного запроса нет.

### Ограниченный реальный smoke test

Явно запускаемый smoke test делает не более двух коротких платных запросов к выбранной модели: один sync и один SSE. Проверяет локальный health endpoint, публичный каталог, успешный ответ, потоковые события, `[DONE]` и наличие usage, если upstream его вернул. Ошибки и disconnect тестируются на fake upstream, а не дополнительными платными вызовами.

### Проверка OpenCode

- Конфигурация выбирает `local/01`, а не upstream ID напрямую.
- OpenCode отправляет запрос на локальный gateway и получает реальный ответ.
- Проверить tool calling через OpenCode, поскольку это обязательная часть агентной работы, а не считать совместимость подтверждённой лишь по обычному текстовому ответу.

## Критерий готовности

Этап готов, когда автоматические тесты проходят, инструкция запуска проверена командами, ограниченный sync/SSE smoke test проходит через реальный NanoGPT, а в OpenCode подтверждён запрос через `local/01`. В отчёте отделить реально выполненные проверки от тех, которые пользователь должен выполнить в своей локальной среде.

## Вне рамок

Биллинг, финансовая БД, Usage/Request Billing, пополнения, сторонние пользователи, дополнительные публичные протоколы и новые модели сверх явно разрешённого allowlist.
