# Исправление конфигурации и обработки ошибок NanoGPT Gateway

**Статус:** выполнено, отчёт см. §12  
**Приоритет:** Высокий  
**Основание:** Статический аудит текущей реализации репозитория `01-gate/01`  
**Область изменений:** Конфигурация приложения, upstream-адаптер NanoGPT, обработка SSE, тесты и документация.

## 1. Цель

Устранить три потенциальных дефекта текущего вертикального среза:

1. Неоднозначный источник конфигурации и зависимость загрузки `.env` от текущей рабочей директории.
2. Некорректная обработка ошибок upstream при потоковой генерации, если ошибка возникает до начала передачи ответа клиенту.
3. Возможная неверная классификация `ConnectTimeout` как ошибки соединения вместо таймаута.

Изменения должны сохранить существующий публичный API и не затрагивать финансовую логику, которая пока не реализована.

## 2. Ограничения реализации

- Сохранить Python + FastAPI и текущую структуру приложения.
- Не менять публичные маршруты и формат успешных ответов.
- Не добавлять новые upstream-endpoint'ы, протоколы и параметры без подтверждения контракта NanoGPT.
- Не реализовывать Usage API, Request Billing, балансы, резервы и списания.
- Не добавлять автоматические повторы запросов к модели.
- Не выполнять платные smoke-тесты без отдельной необходимости и контроля расходов.
- Не переписывать несвязанные компоненты.
- Не хранить SQL-транзакцию или другие долгоживущие блокировки во время генерации.
- Не логировать API-ключи, промпты и содержимое генерируемых чанков.
- Не считать изменение завершённым, пока не пройдены соответствующие тесты.

Перед изменениями агент обязан изучить актуальные файлы и тесты репозитория. Если фактическая реализация отличается от описанной ниже, сначала установить действительное поведение, затем скорректировать реализацию и тесты.

## 3. Исправление № 1. Детерминированная загрузка `.env`

### 3.1. Проблема

Текущая реализация, согласно проведённому аудиту, загружает `.env` относительно текущей рабочей директории и использует поведение, при котором уже установленные переменные окружения имеют приоритет.

Это создаёт два риска:

- Запуск приложения из другой директории может привести к загрузке не того файла или к ошибке отсутствующей конфигурации.
- Конфликтующие переменные окружения могут незаметно переопределить значения из проектного `.env`.

Это не соответствует ожидаемому сценарию локальной разработки, в котором приложение самостоятельно использует конфигурацию своего проекта без ручного `export`.

### 3.2. Требуемое поведение

1. Определять путь к проектному `.env` относительно расположения кода приложения или другого явно заданного корня проекта, а не относительно `cwd`.
2. Сохранить автоматическую загрузку `.env` при штатном запуске приложения.
3. Зафиксировать единственную политику разрешения конфликтов между `.env` и системным окружением.
4. Для локального режима, предусмотренного текущим проектом, значения проектного `.env` должны быть авторитетными, если именно этот файл объявлен единственным источником конфигурации.
5. Если поддержка переменных окружения как способа переопределения необходима для production, разделить режимы явно. Не вводить скрытый приоритет, зависящий от способа запуска.
6. Не выводить значения секретов в диагностические сообщения.
7. Сохранить fail-fast-поведение при отсутствии обязательных параметров.

**Важно:** если текущая архитектура не предусматривает разделения режимов, не добавлять его автоматически. Предпочтительна минимальная реализация с одним документированным правилом загрузки.

### 3.3. Проверки

Добавить тесты, подтверждающие:

- Приложение загружает конфигурацию из проектного `.env`, если процесс запущен из другой рабочей директории.
- При конфликте значений `.env` и окружения действует документированная политика приоритетов.
- Отсутствие обязательного файла или параметров обрабатывается предсказуемо.
- Отсутствие обязательного `NANOGPT_API_KEY` приводит к понятной ошибке запуска.
- Секреты не попадают в сообщения об ошибках.

Тесты должны использовать временные каталоги и изолированное окружение, не зависеть от настоящего NanoGPT API и не читать реальные пользовательские секреты.

### 3.4. Критерий приёмки

Результат одинаково воспроизводим при запуске из корня проекта и из другой рабочей директории. Способ загрузки конфигурации и приоритеты явно описаны в README.

## 4. Исправление № 2. Ошибки upstream до начала SSE-ответа

### 4.1. Проблема

По результатам аудита, потоковая ветка возвращает `StreamingResponse`, а фактическое подключение к NanoGPT выполняется позднее, при итерации асинхронного генератора.

Следовательно, клиент может уже получить HTTP `200 OK`, когда приложение ещё не установило успешное соединение с upstream. Если NanoGPT отвечает ошибкой, возвращает неуспешный HTTP-статус или соединение не удаётся установить, приложение уже не может корректно заменить начальный статус ответа на `502` или `504`.

Текущая обработка ошибок внутри генератора может в результате завершить SSE-поток без корректного HTTP-статуса ошибки.

### 4.2. Требуемое поведение

Разделить потоковую операцию на две логические стадии.

**Стадия A. Подготовка upstream-потока до отправки ответа клиенту**

До возврата `StreamingResponse` приложение должно:

1. Сформировать проверенный payload и upstream-заголовки.
2. Открыть upstream-запрос к NanoGPT.
3. Проверить статус upstream-ответа.
4. Если upstream вернул ошибку до начала передачи тела, прочитать допустимую часть диагностического ответа, безопасно закрыть upstream-ресурсы и преобразовать ошибку в установленный формат ошибки gateway.
5. Только после успешного установления upstream-потока начать передачу SSE клиенту.

На этой стадии должны сохраняться существующие правила безопасности: upstream-credentials не раскрываются клиенту, а содержимое диагностического ответа не передаётся без фильтрации.

**Стадия B. Передача уже открытого потока**

После успешной подготовки:

1. Передавать SSE по мере поступления данных, без полной буферизации генерации.
2. Сохранить существующую фильтрацию служебных данных и поведение относительно `[DONE]`.
3. Корректно закрывать upstream-ответ и HTTP-клиент при нормальном завершении, ошибке и отключении клиента.
4. Не выполнять автоматический повтор генерации.
5. Не пытаться изменить HTTP-статус после начала отправки ответа.
6. Если ошибка возникает после начала передачи тела, корректно завершать поток в пределах возможностей SSE, фиксировать фактическое состояние запроса в логах и не выдавать такой случай за успешную генерацию.

### 4.3. Архитектурное требование

Не открывать второй upstream-запрос ради предварительной проверки. Запрос, который будет передавать данные клиенту, должен быть тем же самым запросом, который прошёл стадию подготовки.

Предпочтительно выделить в upstream-адаптере явную операцию открытия потока и отдельную передачу уже открытого ответа. Интерфейс должен позволять управлять жизненным циклом ответа и клиента без утечек ресурсов.

Не переносить всю реализацию HTTP/SSE в `main.py`, если она относится к ответственности upstream-адаптера.

### 4.4. Обработка ошибок

Сохранить согласованную классификацию:

- Таймаут upstream до начала ответа: HTTP `504`.
- Ошибка соединения, не являющаяся таймаутом: HTTP `502`.
- Неуспешный HTTP-ответ upstream: преобразование в `502` либо другой уже предусмотренный публичный статус согласно текущему контракту gateway.
- Некорректный upstream-протокол или неожиданный формат ответа: `502`.
- Ошибка после начала передачи SSE: не пытаться вернуть новый HTTP-статус; корректно завершить поток и записать ошибку.

Не создавать новые публичные форматы ошибок без необходимости. Сохранить совместимость с существующей обработкой ошибок синхронного режима.

### 4.5. Обязательные тесты

С использованием mock/fake upstream проверить:

1. Upstream возвращает HTTP `401` до передачи тела. Клиент получает корректный HTTP-статус gateway, а не `200`.
2. Upstream возвращает HTTP `429` или `500`. Поведение соответствует принятой политике преобразования статусов.
3. Ошибка соединения до начала ответа приводит к `502`.
4. Таймаут до начала ответа приводит к `504`.
5. После успешного открытия потока клиент получает SSE-чанки по мере поступления, без предварительной буферизации всей генерации.
6. Нормальный поток завершается ожидаемым `[DONE]`.
7. Ошибка после начала передачи тела не приводит к попытке повторно отправить HTTP-статус.
8. При отключении клиента upstream-ресурсы закрываются.
9. При любой ошибке отсутствуют автоматические повторные вызовы генерации.
10. В логах сохраняются диагностические метаданные, но отсутствуют секреты и содержимое промптов.

Тесты не должны обращаться к реальному NanoGPT.

### 4.6. Критерий приёмки

Ошибки, обнаруженные до отправки заголовков клиенту, возвращаются как обычные HTTP-ошибки gateway. После начала SSE корректно обрабатываются только ошибки потока, без ложного утверждения об успешной генерации.

## 5. Исправление № 3. Классификация `ConnectTimeout`

### 5.1. Проблема

По результатам аудита, классификатор upstream-ошибок может проверять `httpx.ConnectTimeout` вместе с ошибками соединения до проверки общего типа таймаута.

Поскольку `ConnectTimeout` является разновидностью таймаута, порядок проверок может приводить к классификации таймаута как ошибки соединения и возврату `502` вместо `504`.

### 5.2. Требуемое поведение

Проверить `_classify` и привести классификацию к явным, непересекающимся правилам:

- `httpx.TimeoutException`, включая `ConnectTimeout`, `ReadTimeout`, `WriteTimeout` и `PoolTimeout`, классифицируется как таймаут и преобразуется в `504`.
- Ошибки соединения, не являющиеся таймаутами, классифицируются как ошибки upstream-соединения и преобразуются в `502`.
- Остальные ошибки классифицируются в соответствии с существующей политикой, без случайного изменения публичного контракта.

Если конкретный тип исключения имеет особую обработку, она должна быть явно обоснована и покрыта тестом.

### 5.3. Обязательные тесты

Добавить отдельные тесты для:

- `httpx.ConnectTimeout`.
- `httpx.ReadTimeout`.
- `httpx.WriteTimeout`.
- `httpx.PoolTimeout`.
- `httpx.ConnectError`.

Проверить как классификацию исключений, так и соответствующий публичный HTTP-статус. Тесты должны выполняться без сети.

### 5.4. Критерий приёмки

Все предусмотренные таймауты последовательно обрабатываются как `504`, а обычные ошибки соединения как `502`. Результат не зависит от порядка случайно пересекающихся проверок в классификаторе.

### 12.1. Описание исправлений

**Исправление №1 (`app/config.py`)** — путь к `.env` теперь вычисляется как `Path(__file__).resolve().parent.parent / ".env"` (функция `default_env_path()`), т.е. от расположения кода, не от cwd. Fail-fast и запрет вывода значений сохранены без изменений.

**Исправление №2 (`app/upstream/nanogpt.py`)** — `run_chat(stream=True)` разделён на две стадии. Стадия A (до возврата генератора, т.е. до `StreamingResponse`): `build_request` с подписью ключа → `send(stream=True)` → проверка статуса; ошибочное тело читается ограниченно (8 KB, не логируется), ресурсы закрываются, поднимается `UpstreamError` → клиент получает обычную HTTP-ошибку gateway (502/504/504^timeout), не `200` с обрывом. Включён catch-all: неожиданный сбой до ответа тоже типизируется. Стадия B: `_stream(client, response, ...)` транслирует **тот же самый** открытый запрос (§4.3 — второй открывается только если первый не удался), фильтрация строк и `[DONE]` сохранены; `finally` закрывает `response` и `client` при любом исходе генератора; необработанный не-`httpx` сбой после начала превращается в типизированный `UpstreamError` и обрывает поток без подделки `[DONE]`. `main.py` не менялся — существующий `try/except` вокруг `run_chat` уже обрабатывает ошибки стадии A, а `sse_nano` — ошибки стадии B.

**Исправление №3 (`_classify`)** — убрана проверка `ConnectTimeout` в ветке соединения; сначала `httpx.TimeoutException` (покрывает `ConnectTimeout`/`ReadTimeout`/`WriteTimeout`/`PoolTimeout`), затем `httpx.HTTPError` как ошибка соединения, затем fallback `protocol`. Любые таймауты → `504`, `ConnectError` → `502`.

1. Политика «окружение приоритетнее `.env`» — обоснованное допущение к условному §3.2.4, а не прямое указание спеки; задокументирована в README и закреплена тестом.
