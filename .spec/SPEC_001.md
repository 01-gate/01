# Локальный FastAPI-приёмник запросов OpenCode

**Версия:** 0.1  
**Статус:** Ready for implementation  
**Язык реализации:** Python  
**HTTP framework:** FastAPI  
**Назначение:** проверить подключение пользовательского OpenCode provider и исследовать фактический формат запросов до реализации AI API gateway.

## 1. Цель

Создать минимальное локальное FastAPI-приложение, которое можно назначить пользовательским провайдером OpenCode через адаптер `@ai-sdk/openai-compatible`.

На данном этапе приложение не генерирует ответы, не обращается к NanoGPT и не реализует биллинг. Оно принимает HTTP-запросы от OpenCode, разбирает JSON и выводит содержимое в удобном для разработчика формате.

Результат этапа: возможность выбрать модель `01` в OpenCode, инициировать запрос и наблюдать фактические HTTP-запросы, формируемые клиентским адаптером.

## 2. Границы реализации

### Входит в scope

- Локальный HTTP-сервер FastAPI.
- Один пользовательский провайдер OpenCode.
- Одна фиктивная модель с ID `01`.
- Конфигурация OpenCode, соответствующая актуальной схеме `https://opencode.ai/config.json`.
- Приём POST-запросов на `/api` и под `/api/`, включая `/api/chat/completions`.
- Разбор JSON и форматированный вывод запроса в stdout.
- Диагностические логи HTTP-метаданных и ошибок разбора.
- Минимальные автоматические тесты.

### Не входит в scope

- Подключение NanoGPT или любого другого upstream.
- Генерация ответов модели.
- Авторизация пользователей и управление API-ключами.
- База данных, Redis, биллинг, резервы и финансовый журнал.
- Реальная реализация OpenAI Chat Completions API.
- Streaming-ответы SSE.
- Tool calling, multimodal processing и преобразование запросов.
- Публичное развёртывание сервиса.

## 3. Конфигурация OpenCode

Создать конфигурационный файл `opencode.json` в корне тестового проекта либо использовать эквивалентную проектную конфигурацию.

Пример:

```json
{
  "$schema": "https://opencode.ai/config.json",
  "model": "local/01",
  "provider": {
    "local": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "Local Gateway",
      "options": {
        "baseURL": "http://127.0.0.1:8000/api"
      },
      "models": {
        "01": {
          "name": "01"
        }
      }
    }
  }
}
```

Требования:

1. `local` является идентификатором пользовательского провайдера.
2. `01` является идентификатором модели внутри провайдера.
3. Полный идентификатор модели в OpenCode: `local/01`.
4. `@ai-sdk/openai-compatible` используется как клиентский адаптер для OpenAI-compatible Chat Completions.
5. `baseURL` указывает на локальный FastAPI endpoint prefix.
6. Конфигурация должна проходить проверку актуальной JSON Schema OpenCode.
7. Не добавлять параметры модели, capabilities и лимиты, если для данного этапа они не нужны.

Проверить фактическое построение URL установленной версией адаптера. Ожидаемый основной маршрут: `POST /api/chat/completions`. Сервер дополнительно принимает `POST /api` для прямой диагностики.

## 4. HTTP-контракт FastAPI

### 4.1. `POST /api`

Принимает произвольное JSON-тело запроса.

Поведение:

1. Прочитать тело запроса.
2. Попытаться разобрать его как JSON.
3. Вывести метод, путь, безопасные заголовки, тип содержимого и размер тела.
4. Если JSON корректен, вывести его форматированно с отступами.
5. Если JSON некорректен, вывести диагностическую информацию без аварийного завершения приложения.
6. Не обращаться к внешним сервисам.
7. Не выполнять генерацию и не изменять входной payload.

### 4.2. `POST /api/{path:path}`

Дополнительно принимать POST-запросы на вложенных путях под `/api/`, включая `/api/chat/completions`.

Для каждого запроса выводить фактический URL-путь. Не предполагать, что OpenCode всегда обращается к одному и тому же endpoint: это проверяется по реальному трафику.

Не добавлять произвольные публичные маршруты за пределами `/api` без необходимости.

### 4.3. Другие методы

На данном этапе не реализовывать каталог моделей, генерацию или иные OpenAI endpoints.

Если OpenCode отправит дополнительные запросы, например `GET` к API, зафиксировать их в логах или явно задокументировать ответ сервера. Не имитировать поддержку endpoint, которого нет.

## 5. Разбор и отображение JSON

Выводить:

- HTTP method и path;
- `Content-Type`;
- размер тела;
- ID модели, если присутствует в JSON;
- сообщения, если присутствует поле `messages`;
- остальные параметры запроса;
- полный разобранный JSON в формате с отступами.

Сохранять исходную структуру данных: вложенные объекты, массивы, числа, строки, boolean и `null`.

Не предполагать, что каждый запрос содержит `model` или `messages`. Любое поле может отсутствовать, иметь неожиданное значение или появиться в будущей версии адаптера.

Для нечитаемого JSON фиксировать ошибку разбора и безопасную диагностику. Сервер должен продолжать принимать следующие запросы.

## 6. Логирование и безопасность

Использовать стандартный `logging` Python либо эквивалентный минимальный механизм.

Логи должны быть ориентированы на разработчика: отдельный блок для каждого запроса, читаемые заголовки и форматированный JSON.

Обязательные ограничения:

- Не выводить значения `Authorization`, `Cookie`, `Set-Cookie` и других потенциально секретных заголовков.
- Не логировать секреты, если они случайно переданы в JSON.
- Не сохранять запросы в файлы или базу данных.
- Не отправлять данные по сети.
- Не публиковать приложение на внешнем интерфейсе по умолчанию.
- Привязать сервер к `127.0.0.1`.
- Установить разумный предел размера входящего тела.
- Не включать traceback в HTTP-ответы клиенту.

Полный вывод payload допустим только как локальный диагностический режим разработки. Он не должен становиться безопасным production-логированием по умолчанию.

## 7. HTTP-ответы

На этапе инспектора задача состоит в приёме и диагностике запроса, а не в реализации совместимого ответа модели.

Допустимо возвращать простой диагностический JSON, например:

```json
{
  "received": true,
  "path": "/api/chat/completions",
  "json_valid": true
}
```

Такой ответ не является ответом OpenAI Chat Completions и не гарантирует успешное завершение запроса в OpenCode.

Если OpenCode требует `choices`, `message`, `finish_reason` или другие поля ответа, это следует зафиксировать как следующий этап. Не выдавать диагностический JSON за настоящую генерацию модели.

Минимальная структура:

```text
/
├── app/
│   ├── __init__.py
│   └── main.py
├── tests/
│   └── test_inspector.py
├── opencode.json
├── requirements.txt

```

Не вводить дополнительные пакеты, слои, интерфейсы, модели базы данных или конфигурационные подсистемы без необходимости.

## 9. Зависимости и запуск

Использовать FastAPI и Uvicorn. Для тестирования использовать pytest и HTTPX, если они нужны выбранному способу тестирования.

Пример запуска:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Конфигурацию `opencode.json` подключить к OpenCode способом, предусмотренным текущей версией приложения.

## 10. Проверки

Автоматические тесты должны подтвердить:

1. `POST /api` принимает корректный JSON.
2. `POST /api/chat/completions` принимает корректный JSON.
3. Вложенные объекты и массивы выводятся без потери структуры.
4. Отсутствие `model` или `messages` не вызывает ошибки обработки.
5. Некорректный JSON обрабатывается контролируемо.
6. Пустое тело и неподдерживаемый тип содержимого обрабатываются предсказуемо.
7. Секретные заголовки не попадают в логи.
8. Превышение лимита размера тела обрабатывается контролируемо.
9. Ошибка одного запроса не останавливает сервер.
10. Ни один тест не требует реального вызова NanoGPT.

Ручной smoke test:

1. Запустить FastAPI.
2. Запустить OpenCode с конфигурацией пользовательского провайдера.
3. Убедиться, что модель `local/01` доступна для выбора.
4. Отправить тестовый запрос.
5. Проверить, какой фактический путь вызвал OpenCode.
6. Проверить JSON и заголовки в терминале.
7. Зафиксировать, какой ответ требуется OpenCode для корректного завершения операции.

## 11. Критерии готовности

Этап считается завершённым, когда:

- FastAPI запускается локально воспроизводимой командой.
- OpenCode распознаёт пользовательского провайдера и модель `01`.
- Фактический POST-запрос OpenCode попадает в FastAPI.
- JSON корректно разбирается и выводится в терминал.
- Ошибочные запросы не приводят к аварийному завершению сервера.
- Секреты не раскрываются в диагностике.
- Автоматические тесты проходят.
- Документированы фактический маршрут и ограничения совместимости.

## 12. Следующий этап

После подтверждения входящего контракта добавить минимальный ответ OpenAI Chat Completions, достаточный для успешного завершения обычного запроса в OpenCode. Только после проверки этого поведения переходить к streaming и интеграции NanoGPT.

На этом этапе не реализовывать upstream-проксирование, биллинг или финансовую модель.
