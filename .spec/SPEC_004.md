# Спецификация: первый рабочий вертикальный срез AI API Gateway на NanoGPT

**Версия:** 1.1  
**Дата:** 2026-10-21  
**Статус:** реализовано, отчёт см. §15  
**Область:** минимальный FastAPI gateway с реальным NanoGPT upstream, без биллинга и PostgreSQL на этом этапе.

## 1. Цель

Подключить существующий gateway к NanoGPT так, чтобы локальные клиенты, включая OpenCode, могли использовать единый OpenAI-compatible интерфейс:

- `GET /v1/models` — публичный каталог разрешённых gateway моделей, **без авторизации**;
- `POST /v1/chat/completions` — синхронные и streaming Chat Completions, с обязательной авторизацией клиентским ключом;
- `/health` — публичная проверка доступности приложения, если этот маршрут уже существует.

На первом этапе нужен один реальный вертикальный срез, а не заготовка полноценного OpenRouter. Не реализовывать Usage API, Request Billing API, клиентский финансовый учёт, балансы, резервы, тарифы или PostgreSQL.

## 2. Зафиксированные решения

1. **NanoGPT inference base URL:** `https://api.nano-gpt.com/v1`.
2. **Отдельная конфигурационная граница для Usage/Billing:** `https://api.nano-gpt.com/api/v1`. Эти endpoint'ы в текущем срезе не вызываются. Переменная нужна как задел для будущего адаптера сверки, а не как универсальная база для всех NanoGPT endpoint'ов.
3. Не пытаться вывести один универсальный префикс из другого URL и не конструировать адреса через эвристики. Для каждого назначения используется собственная настройка.
4. `GET /v1/models` **строго публичный**. Не требовать Bearer token ни в middleware, ни в dependency, ни в обработчике. Это решение должно быть явно отражено в коде, тестах, README и спецификациях.
5. `POST /v1/chat/completions` требует валидный клиентский Bearer key. Проверка выполняется до любого обращения к NanoGPT. Клиентский ключ не передаётся upstream.
6. Вся конфигурация приложения для локальной разработки читается из проектного `.env`. Не требовать от разработчика ручных `export` перед каждым запуском.
7. Не вводить ради этого среза отдельную сложную систему dev-key, CLI, генератор ключей или переменные, которые надо вручную прокидывать в shell. Допустим один фиксированный локальный клиентский ключ из `.env`, сопоставленный с уже используемым ключом в глобальной конфигурации OpenCode. Если текущий глобальный OpenCode `apiKey` уже работает как ключ клиента gateway, конфигурацию OpenCode не менять только ради перехода на `{env:...}`.
8. Не предполагать, что `{env:GATEWAY_TEST_API_KEY}` автоматически загрузит значение из проектного `.env`: это зависит от поведения и расположения конфигурации OpenCode. В рамках среза такая интерполяция не требуется. Сам gateway обязан загрузить `.env` самостоятельно.
9. Удалить `print(messages)`, `print(chunk)` и любые другие диагностические выводы полных prompt/response/chunk. Логировать только безопасные метаданные.
10. В адаптере различать как минимум три идентификатора: JSON response `id`, HTTP `X-Request-ID` и идентификатор/значение, используемое в будущем для Request Billing reconciliation. Не считать их взаимозаменяемыми и не терять ни один из доступных идентификаторов.
11. Существующий интерфейс stub `run_chat()` сохранить. Stub не переписывать ради подключения NanoGPT; реальный адаптер должен соответствовать принятому интерфейсу или подключаться через минимальную абстракцию, не ломая существующие тесты.
12. Не добавлять новые публичные протоколы, endpoint'ы или функции без проверки контракта и тестов.

## 3. Конфигурация через `.env`

### 3.1. Обязательные параметры

Проектный `.env` является единственным источником локальной конфигурации приложения. Приложение загружает его при старте, например через `python-dotenv` или уже используемый в проекте механизм настроек. Не полагаться на наличие значений в shell environment.

Минимальный набор:

```dotenv
# NanoGPT inference API. Используется только для моделей и chat completions.
NANOGPT_INFERENCE_BASE_URL=https://api.nano-gpt.com/v1
NANOGPT_API_KEY=replace_with_private_nanogpt_inference_key

# Клиентский ключ локального gateway. Это не ключ NanoGPT.
# Значение должно совпадать с ключом, которым локальный клиент авторизует POST-запросы.
GATEWAY_TEST_API_KEY=replace_with_local_gateway_client_key

# Отдельная граница для будущих Usage / Request Billing вызовов.
# На первом срезе не используется и не должен инициировать сетевые запросы.
NANOGPT_USAGE_BASE_URL=https://api.nano-gpt.com/api/v1

# Необязательные настройки, если нужны реализации и уже поддерживаются проектом.
NANOGPT_TIMEOUT_SECONDS=90
```

Приведённые значения ключей являются заполнителями, не реальными секретами. Не коммитить реальный `.env`; поддерживать `.env.example` с заполнителями. Если приложение уже использует иные названия переменных, можно сохранить существующие имена при условии, что разделение inference/usage остаётся явным и документация обновлена.

### 3.2. Требования к загрузке

- `.env` загружается автоматически при старте приложения относительно корня проекта или однозначно заданного пути проекта.
- Запуск `uvicorn ...` не должен требовать предварительных `export`.
- Если обязательная настройка отсутствует, приложение должно завершаться с понятной ошибкой конфигурации без вывода значения секрета.
- Нельзя печатать содержимое `.env`, ключи или `Authorization` в логах.
- Секреты читаются из `.env` на стороне gateway. `.env` не передаётся OpenCode и не должен требовать загрузки в глобальный конфиг OpenCode.
- `NANOGPT_USAGE_BASE_URL` на этом этапе только валидируется/сохраняется конфигурацией, если это поддерживается без лишней сложности; не создавать Usage/Billing HTTP-клиент и не вызывать эти endpoint'ы до отдельной задачи.

## 4. Публичный API

### 4.1. `GET /v1/models`

**Авторизация:** отсутствует. Запрос обязан работать без `Authorization`.

Ответ — OpenAI-compatible список моделей, опубликованных самим gateway. Не отдавать весь каталог NanoGPT автоматически. Использовать явный allowlist/конфигурацию существующего проекта и корректно сопоставлять публичный `id` с upstream `model` ID.

Требования:

- публичный model ID не обязан совпадать с upstream ID;
- upstream ID выбирается только из подтверждённого каталога NanoGPT или явно проверенной конфигурации;
- клиенту не раскрывать ключи, внутренние настройки подключения и не относящиеся к публичному контракту upstream-метаданные;
- не обращаться к NanoGPT при каждом `GET /v1/models`, если локальный каталог уже задан конфигурацией/кодом; не вводить удалённую синхронизацию каталога в этот срез;
- сохранять OpenAI-compatible форму ответа, соответствующую тестам и клиентам проекта.

### 4.2. `POST /v1/chat/completions`

**Авторизация:** обязательная.

- Принимать `Authorization: Bearer <gateway-client-key>`.
- Проверять ключ локально до любого платного upstream-вызова.
- При отсутствующем, неверном или отозванном ключе возвращать HTTP 401 в согласованном OpenAI-compatible формате.
- Не передавать исходный клиентский `Authorization` в NanoGPT.
- Upstream-запрос подписывать исключительно `NANOGPT_API_KEY`.
- Проверять, что запрошенная публичная модель существует и разрешена; маппить её в точный upstream ID.
- Поддерживать `stream: false` и `stream: true`.
- Не добавлять поддержку Responses API, Anthropic Messages, embeddings, image/audio/video или tools сверх того, что уже необходимо текущему Chat Completions контракту и подтверждено тестами.

### 4.3. `/health`

Если endpoint уже есть, оставить публичным и не привязывать его к NanoGPT credentials. Не добавлять в healthcheck платный upstream вызов.

## 5. Upstream adapter NanoGPT

### 5.1. Базовый URL и маршрут

Для inference использовать:

`{NANOGPT_INFERENCE_BASE_URL}/chat/completions`

С учётом значения по умолчанию это `https://api.nano-gpt.com/v1/chat/completions`.

Не добавлять `/api` автоматически и не использовать `NANOGPT_USAGE_BASE_URL` для inference. Базовые адреса настраиваются через `.env`, а не зашиваются как единственный вариант в код.

### 5.2. Запрос

- Передавать только нужные поля публичного Chat Completions запроса и поддерживаемые upstream поля.
- Заменять публичный model ID на upstream ID.
- Передавать upstream `Authorization: Bearer ${NANOGPT_API_KEY}`.
- Не передавать клиентский gateway key upstream.
- Настроить конечный timeout и аккуратную обработку сетевых ошибок.
- Не выполнять автоматический повтор платного completion при timeout, разрыве соединения или неоднозначном результате.

### 5.3. Идентификаторы

Для каждого вызова сохранять в безопасных метаданных, если они присутствуют:

- `response_id`: поле `id` в JSON-ответе NanoGPT;
- `upstream_request_id`: HTTP-заголовок `X-Request-ID`;
- `billing_lookup_id`: идентификатор, который будет применяться для будущего запроса Request Billing; по текущим наблюдениям это может быть `X-Request-ID` и/или `x_nanogpt_pricing.requestId`, поэтому значение нельзя молча подменять JSON `id`.

В первом срезе никакого запроса Request Billing не выполняется. Нужно только сохранить и не смешивать доступные идентификаторы. Если значения расходятся, хранить их раздельно. Если потенциальный billing ID доступен только в теле streaming-ответа, извлечь его из финального чанка, не теряя сырой поток для клиента.

### 5.4. Синхронный ответ

- Прозрачно проксировать совместимые данные Chat Completions.
- Не подменять JSON `id` значением `X-Request-ID` и не переписывать их под один формат.
- Не раскрывать `x_nanogpt_pricing` и другие внутренние сведения о себестоимости в публичном ответе, если отдельный публичный контракт явно этого не предусматривает. Не удалять стандартный `usage`, если он есть и разрешён публичным контрактом.
- Если ответ не является ожидаемым JSON, обработать это как upstream protocol error, безопасно залогировать метаданные и не отправлять клиенту полный диагностический ответ upstream.

## 6. Streaming / SSE

При `stream: true`:

- передавать `text/event-stream` поток без полной буферизации;
- передавать SSE data events в исходном порядке;
- не преобразовывать обычные chunk'и в новый формат без необходимости;
- корректно обрабатывать `data: [DONE]`;
- не считать наличие HTTP 200 доказательством успешного финансового завершения запроса;
- не печатать chunk payload или пользовательский текст в логи;
- учитывать disconnect клиента и закрывать upstream stream/соединение корректно;
- не выполнять автоматический повтор генерации при disconnect, timeout или неизвестном исходе;
- при наличии финального usage/pricing chunk извлечь безопасные метаданные, не нарушая SSE-ответ клиенту;
- если финальный usage отсутствует, завершить транспорт согласно фактическому состоянию потока и записать диагностический статус `usage_missing`/аналогичный внутренний статус, не заявляя, что запрос бесплатный.

В предоставленном smoke-примере наблюдались несколько JSON chunks, `data: [DONE]` и финальный chunk с `finish_reason`, `usage` и `x_nanogpt_pricing`. Это наблюдение для выбранной модели и запроса, а не гарантия для всех моделей. Реализация не должна зависеть от того, что финальный chunk всегда имеет точно такую форму.

## 7. Ошибки и неопределённые результаты

- Ошибки клиентской авторизации: HTTP 401, без вызова upstream.
- Неизвестная/неразрешённая модель: клиентская ошибка, без вызова upstream.
- Upstream HTTP error: вернуть безопасную, нормализованную ошибку, сохранив корректный HTTP-контекст настолько, насколько совместимо с публичным API; не раскрывать внутренние заголовки, credentials или сырое диагностическое тело.
- Connect error до отправки запроса: отразить upstream unavailable/ошибку шлюза.
- Timeout или разрыв после возможной отправки запроса: не повторять запрос вслепую. Считать исход потенциально неизвестным, логировать correlation/request IDs, если они известны.
- Ошибка/обрыв SSE после начала ответа: нельзя изменить уже отправленный HTTP status. Закрыть поток корректно, зафиксировать ошибку безопасными метаданными; не притворяться, что stream успешно завершён.
- Отсутствие usage или отсутствие `X-Request-ID` не означает нулевую стоимость. В этом срезе нет списания, но эти случаи должны оставаться видимыми для будущей сверки.
- Не использовать Usage или Request Billing endpoint для автоматического «исправления» ошибки в рамках этой реализации.

## 8. Логирование и безопасность

Разрешённые поля структурированных логов (по мере доступности):

- внутренний correlation ID;
- HTTP route/method/status;
- публичный model ID и upstream model ID, если политика логирования разрешает;
- длительность;
- stream/non-stream;
- наличие/отсутствие upstream `X-Request-ID` и JSON `id` (значения можно хранить в защищённой диагностике, не выводить в публичный ответ без необходимости);
- тип ошибки и upstream HTTP status.

Запрещено логировать по умолчанию:

- полный `messages`, prompt и completion;
- полные streaming chunks;
- `Authorization` и любые API keys;
- содержимое `.env`;
- сырые upstream error bodies без редактирования.

Удалить `print(messages)` и `print(chunk)`. Использовать logger с безопасными полями. Тестом подтвердить, что клиентский prompt, upstream key и client key не попадают в stdout/stderr при обычном запросе и при ошибке.

## 9. Совместимость с OpenCode

- OpenCode использует публичный `baseURL` gateway и свой клиентский `apiKey`.
- Этот `apiKey` является ключом gateway, а не NanoGPT.
- На этом этапе не требовать `{env:GATEWAY_TEST_API_KEY}` и не менять рабочую глобальную конфигурацию OpenCode без необходимости.
- Приложение должно принимать ключ, настроенный в `.env` как `GATEWAY_TEST_API_KEY`. Для локальной разработки пользователь может оставить уже существующий ключ в глобальном `opencode.json` и выставить такое же значение в проектном `.env`. Это простой компромисс текущего среза, а не окончательная схема управления клиентскими ключами.
- Реальная совместимость подтверждается тестом OpenCode против gateway, а не только наличием OpenAI-compatible JSON.
- `GET /v1/models` не должен зависеть от ключа OpenCode, поскольку endpoint публичный.

## 10. Минимальные тесты

### 10.1. Публичные маршруты и авторизация

1. `GET /v1/models` без `Authorization` возвращает 200 и валидную форму каталога.
2. `GET /v1/models` с отсутствующим или произвольным ключом всё равно доступен.
3. `POST /v1/chat/completions` без ключа возвращает 401; upstream не вызывается.
4. `POST /v1/chat/completions` с неверным ключом возвращает 401; upstream не вызывается.
5. `POST /v1/chat/completions` с валидным ключом проходит через stub/mock или тестовый адаптер.
6. Неразрешённая модель отклоняется до вызова upstream.

### 10.2. Конфигурация

7. Приложение читает `.env` автоматически при запуске без ручных `export`.
8. Отсутствующая обязательная настройка приводит к понятной ошибке без утечки значения секретов.
9. Inference URL строится только из `NANOGPT_INFERENCE_BASE_URL`; Usage URL не используется для inference.
10. `NANOGPT_USAGE_BASE_URL` не вызывает сетевые обращения в текущем срезе.

### 10.3. Upstream и протокол

11. Синхронный ответ проксируется в ожидаемой OpenAI-compatible форме.
12. В теле ответа `id` не подменяется заголовком `X-Request-ID`.
13. `X-Request-ID` и `x_nanogpt_pricing.requestId`, если присутствуют, сохраняются раздельно.
14. Streaming передаёт SSE без полной буферизации и корректно завершает `data: [DONE]`.
15. Upstream HTTP error, connect error, timeout и malformed response обрабатываются безопасно.
16. Disconnect/stream failure не приводит к автоматическому повтору запроса.
17. Отсутствие usage или request ID не интерпретируется как нулевая стоимость.
18. Stub API/interface и существующие локальные тесты не ломаются.

### 10.4. Логи и секреты

19. Ни prompt, ни chunks, ни API keys не выводятся в stdout/stderr.
20. Upstream `Authorization` формируется из `NANOGPT_API_KEY`, а клиентский ключ никогда не пересылается NanoGPT.
21. Публичный ответ не раскрывает NanoGPT key, внутреннюю конфигурацию или оптовые pricing details.

### 10.5. Реальные smoke tests

- Сначала выполнить unit/integration tests с mock transport без затрат.
- Затем, если реальные credentials и цена проверены, выполнить максимум один короткий sync запрос и один короткий stream запрос на подтверждённой модели.
- Не повторять платный вызов автоматически после timeout, disconnect или неизвестного результата.
- Не проводить нагрузочные тесты.

## 11. Что не входит в этот срез

- PostgreSQL, миграции и постоянная финансовая модель;
- пользовательские аккаунты и полноценное управление клиентскими API keys;
- баланс, резервирование, ledger, списания, возвраты и тарифные версии;
- вызовы NanoGPT Usage API и Request Billing API;
- сверка и reconciliation;
- Redis, очереди и фоновые workers;
- rate limiting и quotas, кроме уже имеющихся в проекте механизмов;
- автоматическая синхронизация всего каталога NanoGPT;
- Responses API, Anthropic Messages, embeddings, image/audio/video;
- retries платных генераций;
- обещание production-ready биллинга или разрешения коммерческого перепродавания NanoGPT.

Архитектура должна оставить возможность добавить эти части позже, но не реализовывать их преждевременно.

## 12. Документация и файлы, которые должны быть согласованы

При реализации обновить только относящиеся к срезу файлы, не переписывая несвязанные части проекта:

- конфигурацию приложения и `.env.example`;
- `app/main.py` и новый/существующий модуль upstream adapter;
- тесты API, адаптера, streaming и логирования;
- `README.md` — запуск через `.env`, публичность `/v1/models`, авторизация `POST`;
- `AGENTS.md`, `HANDOFF.md`, `TODO.md` и `.spec/*` только там, где они противоречат согласованным решениям.

Все документы должны явно говорить: **`GET /v1/models` публичный, `POST /v1/chat/completions` требует gateway key**. Не оставлять противоположных утверждений в README/spec/tests.

## 13. Критерии готовности

Срез готов, если:

- приложение запускается с настройками из `.env` без ручного `export`;
- публичный `GET /v1/models` работает без авторизации;
- `POST /v1/chat/completions` требует клиентский gateway key и отклоняет неверный ключ до upstream;
- реальный NanoGPT inference использует отдельный inference base URL и server-side API key;
- sync и SSE работают без утечки prompts/chunks/secrets в логи;
- upstream response ID, HTTP request ID и возможный billing lookup ID не смешиваются;
- timeout/disconnect/неполный usage не вызывают слепой retry и не трактуются как бесплатный запрос;
- тесты stub, mock adapter и API проходят;
- README и спецификации не противоречат реализации;
- отчёт об изменениях содержит реальные команды и результаты тестов, а непроверенные сценарии прямо помечены.

## 14. Неопределённости, которые нельзя замалчивать

1. Точная форма каталога NanoGPT и способ его получения не должны угадываться по URL. В текущем срезе публичный каталог gateway задаётся локально; удалённый каталог NanoGPT не требуется для каждого запроса.
2. Семантика `x_nanogpt_pricing.requestId` и отношение к `X-Request-ID` подтверждены только для наблюдавшегося smoke-запроса. Сохранять поля отдельно до дополнительной проверки.
3. Поведение streaming, финального usage и pricing может отличаться между моделями. Не полагаться на единственный пример как на универсальный контракт.
4. Локальный `GATEWAY_TEST_API_KEY` не является полноценной системой клиентских ключей. Его простота намеренна для первого среза; хранение хешей, отзыв, scopes и lifecycle ключей проектируются отдельным этапом.
5. Эта реализация не является финансово безопасным публичным платным gateway, поскольку резервирование средств, идемпотентность биллинга и reconciliation сознательно отложены.
